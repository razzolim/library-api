# v1.0.0 Release Plan — Railway Deployment

## What ships in this release

- `POST /api/auth/login` — credential exchange for a bearer token
- `POST /api/auth/logout` — immediate token revocation (`jti` denylist)
- `POST /api/auth/refresh` — token rotation with reset expiry
- `GET /api/books` — full catalog (list fields, no `summary`/`pdfUrl`)
- `GET /api/books/:id` — single book with `summary` and `pdfUrl`
- `GET /api/changelog` — release history, newest first
- `PATCH /api/users/me/password` — self-service password change

Seed data: 1 demo user (`reader` / `reader`), 12 books, 4 changelog entries.

---

## Target platform: Railway

Two Railway services are needed:

| Service | What | Railway type |
|---|---|---|
| `library-db` | PostgreSQL 16 | Railway PostgreSQL add-on (managed) |
| `library-api` | Node.js API | Railway service from GitHub repo |

Migrations are run as a separate one-time step from your local machine (see Step 3 below).

---

## Prerequisites

- A [Railway account](https://railway.app) with a project created
- The `razzolim/library-api` GitHub repository connected to Railway (or access to deploy from it)
- Docker installed locally (only needed for the migration step — uses the same `liquibase/liquibase:4.29-alpine` image as local dev)
- `psql` or any Postgres client (optional, for verification)
- The Railway CLI installed (`npm install -g @railway/cli`) — optional but useful for environment management

---

## Step 1 — Create the Railway project

1. Go to [railway.app/new](https://railway.app/new) and create a new project named `library`.
2. Note the project ID — you'll use it if you install the Railway CLI.

---

## Step 2 — Provision PostgreSQL

1. Inside the Railway project, click **+ New** → **Database** → **Add PostgreSQL**.
2. Railway creates a managed PostgreSQL 16 instance named `Postgres`.
3. Click the `Postgres` service → **Connect** tab. Railway exposes two URLs — you need both:

   | Railway variable | Hostname pattern | When to use |
   |---|---|---|
   | `DATABASE_PUBLIC_URL` | `*.proxy.rlwy.net` or `*.railway.app` | From your local machine (Step 3) |
   | `DATABASE_URL` | `*.railway.internal` | Inside Railway services at runtime — **not reachable from outside Railway** |

   > **Important:** `DATABASE_URL` (the `.railway.internal` address) only resolves inside Railway's private network. Attempting to connect to it from your local machine produces `UnknownHostException`. Always use `DATABASE_PUBLIC_URL` for any command you run locally.

---

## Step 3 — Run database migrations (local → Railway)

Liquibase runs from your local machine, pointing at Railway's **public** Postgres host.

```bash
# Pull the Liquibase image (same version used in docker-compose.yml)
docker pull liquibase/liquibase:4.29-alpine

# From the Railway Connect tab, DATABASE_PUBLIC_URL looks like:
# postgresql://postgres:<password>@<host>.proxy.rlwy.net:<port>/railway
#
# Resolve the Railway host IP first (needed for --add-host below):
nslookup <host>.proxy.rlwy.net
# Note the IP address returned (e.g. 66.33.22.219)

# Railway requires SSL — append ?sslmode=require to the JDBC URL.
docker run --rm \
  --add-host <host>.proxy.rlwy.net:<ip> \
  -v "$(pwd)/liquibase:/liquibase/changelog" \
  -e LIQUIBASE_SEARCH_PATH="/liquibase/changelog" \
  -e LIQUIBASE_COMMAND_URL="jdbc:postgresql://<host>.proxy.rlwy.net:<port>/railway?sslmode=require" \
  -e LIQUIBASE_COMMAND_USERNAME="postgres" \
  -e LIQUIBASE_COMMAND_PASSWORD="<password>" \
  -e LIQUIBASE_COMMAND_CHANGELOG_FILE="changelog-master.yaml" \
  liquibase/liquibase:4.29-alpine update
```

The username for Railway's managed Postgres is always `postgres`. Extract `<password>`, `<host>`, and `<port>` from the `DATABASE_PUBLIC_URL` value in the Connect tab.

> **SSL required:** Railway's managed PostgreSQL enforces SSL. Without `?sslmode=require` on the JDBC URL, the connection will be refused even with correct credentials.

> **Docker Desktop DNS:** Docker Desktop (Linux and macOS) runs containers in a VM whose Java DNS resolver does not always inherit the host's DNS. The `--add-host` flag injects the Railway hostname directly into `/etc/hosts` inside the container, bypassing this issue. Re-run `nslookup` if Railway ever rotates the IP.

> **Search path:** `LIQUIBASE_SEARCH_PATH` must be set explicitly when running Liquibase via `docker run`. Without it, Liquibase cannot locate `changelog-master.yaml` even though the volume is mounted correctly.

**Expected output:** Liquibase will log one `ChangeSet … ran successfully` line per changeset (4 tables + indexes) and exit with code 0. If it reports `Checksum mismatch` on any changeset you already applied, see the [troubleshooting](#troubleshooting) section.

> **Why local and not a Railway service?** For a first-ever deployment there is no live database to protect, so running migrations from a local machine is the fastest, lowest-risk option. For future releases, add a dedicated `library-migrate` Railway service (see [Repeatable migration service](#repeatable-migration-service-future-releases)) that you trigger before each API deploy.

## Step 4 — Deploy the API service

### 4a. Create the Railway service

1. Inside the Railway project, click **+ New** → **GitHub Repo**.
2. Select the `razzolim/library-api` repository.
3. Railway will detect the `Dockerfile` and use it automatically.
4. Set the **Root Directory** to `/` (the repo root, where the `Dockerfile` lives).

### 4b. Set environment variables

In the service's **Variables** tab, set the following. Railway will inject them into the container at runtime.

| Variable | Value | Notes |
|---|---|---|
| `DATABASE_URL` | *(link to Postgres add-on)* | Click **+ Add Reference** and select the `Postgres` service's `DATABASE_URL` (internal URL). Railway wires it automatically. |
| `JWT_SECRET` | `<long-random-string>` | Generate with `openssl rand -hex 32`. Keep it secret. |
| `JWT_EXPIRES_IN` | `1h` | Adjust if you want a shorter or longer token lifetime. |
| `CORS_ORIGIN` | `https://<your-frontend-domain>` | The production URL of your `library-portal` frontend. Comma-separate multiple origins if needed. |
| `PORT` | `3000` | Must match the `EXPOSE` in the Dockerfile. Railway reads this automatically if you leave the service's port setting at "auto-detect". |
| `DEMO_USER_USERNAME` | `reader` | |
| `DEMO_USER_PASSWORD` | `reader` | Override for a non-demo deployment. |
| `DEMO_USER_FULL_NAME` | `Demo Reader` | |
| `DEMO_USER_ROLE` | `reader` | |
| `ADMIN_USER_USERNAME` | *(your choice)* | Optional. If set, an admin account is seeded on every deploy. |
| `ADMIN_USER_PASSWORD` | *(your choice)* | Required when `ADMIN_USER_USERNAME` is set. Use a strong password. |
| `ADMIN_USER_FULL_NAME` | *(your choice)* | Required when `ADMIN_USER_USERNAME` is set. |

> `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` are **not** needed in Railway — they're only used by `docker-compose.yml` to configure the local `db` container. On Railway, `DATABASE_URL` is all Prisma needs.

### 4c. Deploy

1. Click **Deploy** (or push a commit to `main` if you've enabled auto-deploy).
2. Railway builds the image from the `Dockerfile`, seeds the database, and starts the server.
3. The startup sequence in the container is: `node prisma/seed.js && node src/server.js` (see `Dockerfile` CMD).
   - The seed script is idempotent — it upserts, so re-deploying never duplicates data.
   - If `JWT_SECRET` or any `DEMO_USER_*` variable is missing, the container exits immediately with a descriptive error in the Railway logs.

### 4d. Expose a public URL

In the service's **Settings** tab, click **Generate Domain** (or use a custom domain). Railway assigns a `*.up.railway.app` URL. This is the `VITE_API_BASE_URL` you set in the `library-portal` frontend's production environment.

## Step 5 — Post-deployment smoke test

Replace `<api-url>` with your Railway-generated domain.

```bash
# 1. Login — expect 200 with success:true, user, and a token
curl -s -X POST https://<api-url>/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"reader","password":"reader"}' | jq .

# 2. Save the token
TOKEN=$(curl -s -X POST https://<api-url>/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"reader","password":"reader"}' | jq -r .token)

# 3. Fetch books — expect 200 with a 12-item array
curl -s https://<api-url>/api/books \
  -H "Authorization: Bearer $TOKEN" | jq 'length'

# 4. Fetch changelog — expect 200 with a 4-item array, newest first
curl -s https://<api-url>/api/changelog \
  -H "Authorization: Bearer $TOKEN" | jq '.[0].version'

# 5. Refresh token — expect 200 with a new token
curl -s -X POST https://<api-url>/api/auth/refresh \
  -H "Authorization: Bearer $TOKEN" | jq .

# 6. Logout — expect 200 { success: true }
curl -s -X POST https://<api-url>/api/auth/logout \
  -H "Authorization: Bearer $TOKEN" | jq .
```

All six checks passing means the deployment is healthy.

## Repeatable migration service (future releases)

Once the project has a live database, edit-in-place changesets are no longer safe (Liquibase checksums the applied entries and will refuse to reapply a changed one). At that point:

1. Add new changeset files to `liquibase/changesets/` for each schema change (e.g. `005-add-borrow-table.sql`).
2. Create a `Dockerfile.migrate` at the repo root:

   ```dockerfile
   FROM liquibase/liquibase:4.29-alpine
   COPY liquibase/changelog-master.yaml /liquibase/changelog/
   COPY liquibase/changesets/ /liquibase/changelog/changesets/
   ENTRYPOINT ["liquibase"]
   CMD ["update"]
   ```

3. Add a `library-migrate` Railway service pointing at the same GitHub repo, with **Dockerfile Path** set to `Dockerfile.migrate` and the same `DATABASE_URL` reference.
4. Before each API release: trigger the `library-migrate` service manually (or via a Railway deploy hook), wait for it to exit `0`, then deploy the API.

---

## Rollback

Because this is the first deployment there is no prior state to roll back to. For future releases:

- **API rollback:** in Railway, open the `library-api` service → **Deployments** and click **Redeploy** on the previous successful deployment.
- **Database rollback:** Liquibase changesets include `--rollback` SQL (e.g. `DROP TABLE ...`). Run rollback from the same `docker run` command used in Step 3, replacing `update` with `rollbackCount 1` (or the target tag). Only roll back the database *after* the API is rolled back, not before.

## Troubleshooting

**`Checksum mismatch` from Liquibase**
The changeset SQL was edited after it was applied to this database. Since this is a pre-v1.0.0 database you'd normally drop and recreate it. If it's a live database you care about, do not edit the changeset in place — add a new one instead.

**Container exits immediately on Railway**
Check the Railway build/deploy logs. The most common causes:
- `JWT_SECRET environment variable is not set` — add `JWT_SECRET` in the Variables tab.
- `DEMO_USER_USERNAME environment variable is not set` — all four `DEMO_USER_*` vars must be set.
- Prisma `connect` error — confirm `DATABASE_URL` references the correct internal URL and that the `Postgres` add-on is running.

**CORS errors in the browser**
Confirm `CORS_ORIGIN` is set to exactly the frontend origin (protocol + domain + port, no trailing slash). Check for mismatches between `http` and `https`.

**Login returns 401 even with correct credentials**
The seed may not have run. Check the Railway logs for `Seeded 1 user, 12 books, and 4 changelog entries.` If absent, the seed script threw before completing — most likely a missing `DEMO_USER_*` variable.
